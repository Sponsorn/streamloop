# Architecture

How the parts fit. Direction, decisions and spike results live in the Notion pages named at the end; this file is structure only.

## What it is

Streamloop restreams a YouTube playlist to Twitch around the clock from one Windows box. This branch holds **3.0**: a headless ffmpeg pipeline under a Rust supervisor (`supervisor/`), with no mpv, OBS or desktop session, driven over local HTTP by the Node/TypeScript backend in `src/`. Node owns the config, the dashboard, Discord alerts, the Twitch checks and the updater, and launches the supervisor. `spikes/` keeps the spikes that proved the pipeline. **2.x**, the live release (mpv and OBS), lives on the `2.x` branch.

R1 ports the Node backend to Rust: `streamloop.exe [--root DIR]` runs the control process (`crates/control`) behind the same REST API (see Control mode (R1)). `START.bat` now starts that exe (see `scripts/START.bat` below); the release ZIPs still carry Node until R1 switches them over, and the sections that name Node describe that release.

## 2.x (the `2.x` branch)

This section describes the `2.x` branch. None of these mpv or OBS modules exist in `src/` on this branch.

- `src/server/index.ts`: wires every component by dependency injection, serves `/admin` and `/overlay`, opens the admin page on boot unless `autoOpenAdmin` is off, exits 75 after a staged update.
- `config.ts` / `types.ts`: Zod schema and defaults for `config.json` (gitignored), hot reload via `POST /api/config`.
- `state.ts`: playback position in `state.json`, debounced 2 s writes, suppressed during recovery.
- `mpv-client.ts` / `mpv-args.ts`: spawns mpv, talks JSON over the named pipe, polls properties, receives events.
- `recovery.ts`: 5 s heartbeat, stall / video-freeze / premature-EOF / non-playing detectors, in-place URL retry, then RetryCurrent, RestartMpv, CriticalAlert.
- `frame-monitor.ts`: hashes OBS screenshots to catch a frozen picture mpv reports as healthy.
- `obs-client.ts`: obs-websocket connection, streaming control, screenshots.
- `playlist-metadata.ts`: yt-dlp flat playlist fetch, cached for the dashboard.
- `event-store.ts`: recovery timeline as daily JSONL in `logs/`.
- `discord.ts`: webhook notifications with templates.
- `twitch.ts`: Twitch liveness check (app token + Helix streams) cross-checked with OBS's streaming state.
- `api.ts`: REST surface for the dashboard and overlay; masks secrets in `GET /api/config`.
- `updater.ts` / `full-update.ts` / `ytdlp-updater.ts`: GitHub Releases updater (own major only, 3.x from prereleases; SHA-256 verified; an app-only update takes the slim ZIP and swaps `app\` and `START.bat`, a full update takes the full ZIP and also swaps the parts the release's `components.json` names as changed); yt-dlp self-update.
- `logger.ts` / `file-log-transport.js`: pino to console and file.
- `spawn-cwd.ts`: the temp folder every child process starts in, so nothing holds `app\` during the update swap.
- `src/admin/`: dashboard (status, timeline, transport, config, update button). `src/overlay/`: now-playing page for the OBS Browser Source.
- `scripts/START.bat`: preflight (`streamloop.exe`, `ffmpeg\`, `node\`, `pot\`; an exe left as `streamloop.exe.old` by a cut-off update is renamed back first), then `streamloop.exe` in a loop with `STREAMLOOP_START` set to `first`, then `restart`, or `rollback` for the run after a rollback. Exit codes: 0 stay down, 2 another StreamLoop holds the port (stays down with a message), 75 restart after 10 s without the rollback check, else restart after 10 s; after a crash with `_update\landed` and `streamloop.exe.old` present it puts the previous exe back (`:rollback`). It swaps nothing and replaces nothing, itself included.
- `build/prepare-release.js`: on this branch it builds the 3.0 release ZIPs (see Supervisor interface, Packaging); 2.x builds from the `2.x` branch.
- `shell/`: Tauri thin shell (stage 1 of the standalone admin UI track) that shows the local `/admin` in WebView2; not part of the release ZIP yet.

## Supervisor interface (3.0)

- **Install layout** under the root (`--root`, default the exe's folder; `supervisor/src/paths.rs`): `ffmpeg\ffmpeg.exe`, `yt-dlp\yt-dlp.exe`, `yt-dlp\deno.exe`, `yt-dlp\plugins\`, `pot\build\main.js` (token server), `node\node.exe`, `supervisor\streamloop-supervisor.exe`, `supervisor\slate.mp4`, `app\config.json`, `data\`. Every tool is called by full path, never through PATH; yt-dlp gets `--ffmpeg-location` for its merge.
- **Packaging** (`build/prepare-release.js`): `cargo build --release -p streamloop` at the repo root, then the install layout in `build/release-layout.js`: `streamloop.exe`, `START.bat`, `app\config.example.json`, `supervisor\slate.mp4`, `ffmpeg\`, `yt-dlp\` (with deno and the plugin zip), `pot\`, `node\` and `data\`. `pot\` is the bgutil token server (2.0.0) built under the bundled Node. The build writes `dist/streamloop-vX.Y.Z.zip`, `dist/streamloop-vX.Y.Z.exe` (the updater's download), a `.sha256` for each and `dist/node-version.txt`; there is no update ZIP and no `components.json`. No ZIP ships `app\config.json`; the control process creates it from `config.example.json` on first start, so a reinstall keeps the user's. `crates/streamloop/tests/release_layout.rs` checks the layout against `Layout` in `crates/common/src/paths.rs`, and `build/verify-release.mjs` checks the ZIP and that its exe prints the ZIP's version.
- **CLI:** the supervisor is one mode of `streamloop.exe`, built from the Cargo workspace at the repo root (`crates/streamloop` is the exe, `supervisor/` the library it calls). Its first argument picks the mode: `supervisor`, `launch`, `protect`, `check`, `--version`; none is the control process (`streamloop.exe [--root DIR]`, see Control mode (R1)), and any other argument prints the usage line and exits 64. `streamloop.exe supervisor [--root DIR] [--config FILE] [--data DIR]`; the default root is the exe's own folder. Dev only: `--target URL` (replaces ingest and key, for local MediaMTX) and `--debug-faults`, which also unlocks the test knobs (`--url-ttl-s`, `--url-refresh-margin-s`, `--limit-rate`, `--start`, `--max-videos`, `--hours`). `streamloop.exe launch ARGS` starts `streamloop.exe supervisor ARGS` through a short-lived intermediate: it re-execs the same exe detached, in a new process group and outside the caller's job (`CREATE_BREAKAWAY_FROM_JOB`; when the job refuses breakaway it starts inside the job instead), logs a `launched` event with `breakaway: true|false`, waits up to 3 s for the port to answer or the child to exit, and exits 2 when the child found the port taken, 3 when it refused `config.json`, else 0. The supervisor binds its port before it reads `config.json`, so 2 only ever means the port is taken; a refused config logs a critical `config-refused` event with the reason and exits 3. Any other exit during the wait is 1. `streamloop.exe check` (the same flags as `supervisor`) proves the binary runs without streaming: it reads `config.json` as startup does, requires every install-layout file, runs `ffmpeg -version` and starts the token server on port 4418, pinging `/ping` once a second until it answers, for up to 15 s from its start (the grace the supervisor's own token watchdog gives a new server), then stops it; it binds neither 4417 nor 4416, enters no job and touches neither cache nor state. It prints `ok` and exits 0, else prints `streamloop-supervisor check: <reason>` on stderr and exits 1; the prefix stays while Node's health check, which runs it through `supervisor\streamloop-supervisor.exe`, strips it. `streamloop.exe protect` reads a stream key on stdin and prints a DPAPI blob (current user) for `supervisor.streamKeyProtected`.
- **Config** (`app\config.json`, owned by Node): `playlists` (each `id`, in play order) plus a `supervisor` object: `ingestUrl`, `streamKeyProtected`, `encoder`, `cacheBudgetMb`, `readAheadSeconds`, `playerClient`, `overlay`, `freezeSeconds`, `silenceSeconds` (minimums: read-ahead 2 s, freeze and silence 5 s, cache 50 MB), and the top-level `ytdlCookiesFromBrowser` it shares with Node (empty for none; passed to every yt-dlp call as `--cookies-from-browser`, applied live). The supervisor reads it read-only through `streamloop_common::config`, the same schema as Node's `config.ts`: a blank `ingestUrl` or `playerClient` and a missing `supervisor` object mean the defaults, and an empty `streamKeyProtected` means no key. Read at start and on `POST /reload`, which applies what it can live, reports `restartRequired` for ingest, key, encoder and the freeze and silence durations, and brings the ring in line with `playlists` (see Playlists under Main flows). Nothing writes the order back: it stays as the user set it.
- **HTTP** on 127.0.0.1:4417 (the request and reply shapes live in `streamloop_common::api`): `GET /status` (`state`: `starting`, `playing`, `recovering`, `needs-stream-key`, `waiting-for-playlist`, `stopping`; `reason`; `streamKeyProblem`; now playing, with `playing.playlistId` naming the list on air, and `playing.index` and `playlistCount` counting within it; `version` (the exe's build version); encoder alive, speed, CPU and `uptimeS` (whole seconds since the encoder started, `null` with none); watchdog; YouTube breaker; token server), `POST /control` (`{"cmd"}`: `next` and `prev`, which cross into the neighbouring list at a list's end, `restart`, `jump` with an `index` in the list on air and an optional video `id` that wins when the ring has it, or `restart-encoder` with an optional `reason` of up to 200 characters), `POST /reload` (optional `{"playlist", "index", "id"}`: `playlist` goes to that configured list and refuses any other, `index` and `id` say where in it to start, by id when the list has it, else the index clamped to the list; a supervisor before `playlist` existed plays only `playlists[0]` and names no list in `/status`, and Node then answers that the full ZIP is needed), `POST /shutdown`, and `POST /debug/fault` only with `--debug-faults`. With no usable key it stays up in `needs-stream-key` and a reload with a working key starts the encoder.
- **Data** (`data\`): `state.json` (resume point: the list on air, the video's id and number in that list, its position), `cache\` (finished `<id>.mp4` downloads survive a restart and count toward the budget once a list names them; partial files are removed at start, and files no video claims once every configured list has answered), `logs\` with daily files (`supervisor-events-DATE.jsonl`, named apart from Node's own `events-DATE.jsonl` so both fit in one folder; up to 3.0.4 it was `events-DATE.jsonl`, which Node still reads; `seams-`/`controls-`/`encoder-`/`downloads-`/`deletes-`/`buffer-DATE.csv`, `ytdlp-`/`tokenserver-DATE.log`), one log per ffmpeg process, `run.json` and `playlist.json` (the list on air with its playlist id, played when the fetch at start fails); a week is kept and the key is redacted from all of it. Video numbers in events and CSVs count within their list, so `id` is what tells two lists' videos apart. `stopped-by-user` is Node's marker for a dashboard Stop: written on Stop, removed on Start and read when Node starts, so a stopped stream stays stopped across Node restarts. `waiting-for-start` is Node's marker for a start held until Start, so a crash restart keeps holding. `update-state.json` is Node's record of a full update (from and to version, parts, folders, step, result, reason, the encoder baseline and the download percentage), read through `/api/update/status`. `update-swap.log` is `START.bat`'s record of a part swap (`<folder> <status> <detail>`), `update-swapping` exists while it swaps or rolls back, and `update-checking` exists from a part swap until the new version passes its health check.
- **Twitch read-back** (Node, `twitch-readback.ts`): every 5 min while live, two frames of the channel's own HLS 5 s apart through `ffmpeg\ffmpeg.exe`; if the overlay clock stands still twice in a row while Helix says live, Node restarts the encoder, at most once per 30 min, then only alerts.
- **Launch by Node** (`supervisor-launcher.ts`): Node polls `GET /status` every 2 s and, after 3 misses, runs `ROOT\supervisor\streamloop-supervisor.exe launch --root ROOT` hidden and with no stdio (backoff 10 s, 30 s, 60 s, 5 min). An exit code 2 from the intermediate means another supervisor holds the port, and Node attaches to it. Exit 3 counts as down, and `/api/status` shows "The supervisor refused config.json: <reason>" (from the last `config-refused` event) until a supervisor answers. `POST /api/config` refuses a `ytdlCookiesFromBrowser` over 200 characters or with a control character, so a save cannot write a config the supervisor refuses. `START.bat` sets `STREAMLOOP_START` (`first` after the window opens, `restart` after a crash or an app-only update, `update` for the first start after a part swap, `rollback` for the first start after a rollback); with `autoStartStream` off, a `first` or `rollback` start holds the launch (`data\waiting-for-start`, launcher state `ready`) until Start, and a `restart` keeps holding only while that marker exists. An `update` start, or any start that finds `data\update-checking` while the update is at `swap` or `check` (or none is recorded), holds until the new version passes its health check and then follows the setting. Recovery ignores the hold: a supervisor that answers is attached and ends the hold, and one that dies is relaunched. It never stops the supervisor except for the dashboard's Stop stream, after which it relaunches nothing until Start, also across Node restarts through `data\stopped-by-user`. ROOT is the parent of `app\` when `node\` sits beside it, else `STREAMLOOP_ROOT` (dev). `STREAMLOOP_DEBUG_FAULTS=1` adds `--debug-faults`, for test runs only.
- **Measuring harness:** `supervisor/scripts/` (`dev-root.mjs` builds a dev root in this layout, with the built exe linked as `ROOT\streamloop.exe`; `session.mjs` runs one supervisor session, `streamloop.exe supervisor`, against local MediaMTX, `drive.mjs` drives it over HTTP only, `analyze.mjs` computes the verdict; `node-session.mjs` starts `ROOT\streamloop.exe` from a launcher console as `START.bat` does and drives the control process's API through runs A, B, C and treekill, telling the control process and the supervisor apart by command line, and prints each run's verdict; `install-session.mjs` installs `dist/`'s full ZIP in a temp folder and takes it through exe updates (planned break, Update Now, a landing while stopped), both rollbacks, the move from v3.0.5 and the gate's faults, against a local release list given by `STREAMLOOP_TEST_RELEASES` and test builds of `streamloop.exe` it makes with cargo; `update-session.mjs` takes a Node install through master's full updates; `install-kit.mjs` holds the helpers they and R3's `ui-session.mjs` share).

## Main flows (3.0)

- **Seam.** A new feeder starts when the timeline is less than 20 s ahead of the encoder. It begins at timeline offset = last video PTS written + one frame, so timestamps stay continuous. The encoder never sees a seam as anything but more MPEG-TS.
- **Playlists.** Every configured list's videos sit in one ring, in the configured order rotated to start at the list loaded first, so each list keeps the one that follows it. Seams, look-ahead downloads, retries and skips work on ring positions and never see a list boundary: the last video of a list is followed by the next list's first video like any other seam, and the last list by the first. A single list wraps to its own first video. The list a start or reload asks for loads first; the others join behind it one at a time once a video is on air and none waits for YouTube. A list that will not load is reported once (`playlist-failed`), tried again every 10 min, and counts toward the breaker only for a bot check. When a list ends while another is still missing, `playlist-advance` or `playlist-restart` goes critical, since that is when it costs viewers something. A list joining at the end moves no video; a reorder or a dropped list lays the ring out again and jumps to the video on air at its position. A reload naming a list in the ring jumps there without a fetch, and a reload naming none stays on the list on air while the config has it.
- **Control (next, prev, restart, jump).** All four are `switch(index, 0)` computed from `P_view` (what the viewer sees, not what the feeder has reached): kill the feeder, flush the queue from the first video PES at least 1 s past the writer, start the target feeder on the continuing offset from the cached file or, if not on disk, its URL (slate covers the resolve). Last command wins. `restart-encoder` (for Node's Twitch checks) takes the encoder-down path of recovery step (3) and logs `encoder-restart-requested` with the caller's reason; while a restart is already pending it answers `alreadyRestarting: true`, and in `needs-stream-key` it answers 400.
- **Cold start.** The list `state.json` names is fetched first, or the first configured one if the config no longer has it or `state.json` names none (a position saved for a list that is no longer configured is not used); if that fails and `playlist.json` holds the same playlist id, that list plays (`playlist-from-saved`) while the fetch is retried through the gate. A resume whose video is in the cache plays from the file at once, with no slate wait and no resolve. Otherwise: slate on air at once; the first video's URL is resolved (`yt-dlp -j`, waits for `available_at`) and switched in; the downloader fetches that video first; when the file is complete the URL feeder is killed and a file feeder continues at `P_fed` with no flush.
- **Recovery.** (1) Feeder fails, stalls (no video PES for 10 s) or ends early: restart in place at `P_fed`, 2 tries per video. A file feeder that fails before its first frame drops its cached file, so the retry plays the URL; a later failure keeps the file and retries from it. A picture the encoder's `freezedetect` finds frozen for `freezeSeconds` (counted from 5 s into a seam, never on the slate) takes the same ladder: retry, retry, skip. Audio silent for `silenceSeconds` is reported only (outcome `content`): the feeder carries audio and video as one stream, so a broken audio stream stalls the feeder or ends it early, which step (1) catches, while silence under a moving picture is the video's own ("brb" stretches). Silence never restarts or skips anything. (2) Then skip; 3 skips in a row is critical. A video YouTube will not serve (removed, private, blocked, age-gated) is skipped at once; from the third such video in a row (no successful resolve between them) each one counts toward the breaker. When every video has been skipped, the slate airs for 60 s, doubling to 30 min, before the list is tried again. (3) Encoder exits or its progress stops for 10 s: restart with backoff (2, 5, 10, 30, 60 s); current video resumes at `P_view`. While it waits, a thread off the control loop tries a TCP connection to the ingest every 2 s (port 1935 for `rtmp://` and 443 for `rtmps://` when the URL names none, as Twitch's does), and an ingest seen down that answers again restarts the encoder at once (`encoder-start` carries `ingestBack: true`). The `encoder-exit` event carries `uptimeS`; Node reads a first exit after 47.5 h as Twitch's 48 h broadcast limit and sends no Discord alert for it or its restart. (4) Supervisor crash: Job Object kills every child, Node relaunches it, it resumes from `state.json`.
- **Full update.** Only for a release whose `components.json` names a part that differs from the install; the stream is off air from the stop to the start. Each step goes into `data\update-state.json`. (1) `download`, still on air: while a second `START.bat` window of the install runs (a `cmd.exe` whose command line names `ROOT\START.bat` and that runs a program besides its console host; an idle prompt the trampoline's `cmd /K` window leaves behind does not count; only `cmd.exe` command lines are read, so the encoder's stream key never reaches Node), the update does not start and the dashboard shows "Close the other StreamLoop window first.", since that window's heal would roll the swap back under it. Otherwise earlier `_update_old*` / `_update_bad_*` copies and a stale `data\update-checking` are removed (one that cannot go calls the update off), a test encode with the configured encoder on the installed ffmpeg is kept as the baseline, and the full ZIP is downloaded with its percentage shown, verified, extracted and staged in `_update_tmp\` (`app\`, `START.bat`, the changed parts' folders and `yt-dlp\`). (2) `stop`: a second window found now fails the update here, with nothing stopped. Otherwise Node stops its own timers, posts "Updating to {version}, the stream is off air until it is done." to Discord, and stops the supervisor with `POST /shutdown` (twice, then by force) until `/status` is silent and nothing runs from `supervisor\`, then waits for, and from the second try ends, whatever runs from the folders being replaced. Each of those waits gets 3 tries. A try looks up to 11 times, a second apart, each look a PowerShell listing of the running programs, so a try that does not succeed takes well over 10 s. A stop that fails calls the update off (`failed` at `stop`) and the old supervisor comes back. (3) `swap`: Node exits 75 and `START.bat` swaps the parts, each rename with 3 tries, then `app\`, putting every part back if one fails. (4) `check`: the new Node starts with `STREAMLOOP_START=update`, holds the launcher and checks every install file the supervisor needs (not the Windows overlay font), the configured encoder against the baseline (an encoder that already failed is not the update's fault) and `streamloop-supervisor.exe check`, each item with 3 tries. Pass: `ok` at `start`, then `data\update-checking` is removed and after it the old copies, and with `autoStartStream` on and no Stop pressed the stream starts, `done` once `/status` reports `playing` with a live encoder, and Discord gets "Back on air on {version}."; a stream held for Start gets "Updated to {version}. Ready to stream." instead. Fail: `failed` with the reason, exit 76, and `START.bat` puts the old version back and starts it with `STREAMLOOP_START=rollback`, which marks the update `rolled-back`; three crashes during the check do the same. A start that finds the update cut off marks it `failed` (download or stop: the old version never left) or `rolled-back` (swap or check: heal put the old version back). `START.bat` writes `data\update-checking` before it removes `data\update-swapping`, so new parts are never left with neither marker. Each update that does not go through is posted to Discord once, by the Node that records the result: "The update to {version} failed at {step}: {reason}. Still on {old}." The dashboard's Stop, Start, controls, saves, yt-dlp update and setup check answer 409 throughout, and Update answers 409 while an update check runs.

## Control mode (R1)

`streamloop.exe [--root DIR]` runs the control process (`crates/control`), the port of `src/server/`: the dashboard and its REST API on 127.0.0.1:7654, Discord, the Twitch checks, the launcher and the updater. Each Node module has a Rust module with the same behaviour, timings and texts; `app.rs` is `index.ts`.

- **Root and files.** `--root`, else the exe's folder when it holds `app\`, else `STREAMLOOP_ROOT`; with none it prints "No install root: run streamloop.exe from the install folder, or pass --root." and exits 1. A root that did not come from the exe's folder is dev mode, where the updater only checks. It reads `ROOT\app\config.json` (created from `app\config.example.json` when missing) and writes its log (`streamloop-DATE.log`) and timeline (`events-DATE.jsonl`) to `ROOT\app\logs\`, in release and dev alike, 7 days kept. The dashboard's files are built into the exe.
- **Start order**, as `index.ts`: load the config; bind the port (taken: "Port 7654 is in use. Is another StreamLoop running? Stop it and this one starts by itself." and exit 2, so `START.bat` can tell another StreamLoop from a crash); remove the 3.0 leftovers; settle an update that was cut off, or start confirming one that landed; the launcher, the events tail and the Twitch checks unless it is a first run (the wizard's first save starts them); the update checks (30 s after start, then every `updateCheckIntervalMs` while `autoUpdateCheck` is on) once no confirmation runs; the yt-dlp self-update; `autoOpenAdmin`.
- **3.0 leftovers**, removed by name at every start: `app\src`, `app\node_modules`, `app\package.json`, `app\package-lock.json`, `app\tsconfig.json`, `app\node-version.txt`, `supervisor\streamloop-supervisor.exe`, `_update_tmp\`, `_update_old\`, `START.bat.new`, `_apply_launcher.bat`, and a full update's `_update_old_<part>\`, `_update_bad_<part>\`, `_update_bad_app\`, `data\update-swapping`, `data\update-checking` and `data\update-swap.log`. `app\config.json`, `app\logs\`, `data\` and `_update\` stay.
- **Launcher.** It runs `ROOT\streamloop.exe launch --root ROOT`, the same intermediate. The control process keeps its stdin, stdout and stderr out of its children, so the supervisor holds neither its console nor a file its output was redirected to, and a launcher that redirects to that file can start it again. It has master's start holds: `STREAMLOOP_START` (`first`, `restart`, `rollback`) and `autoStartStream` decide whether the start waits for Start. Every start that finds a landed update holds launches until its confirmation ends (a supervisor that answers is still attached); after it, a stream that was held before the landing stays held, and any other carries on. A supervisor that reports another version than the control process, or none (a 3.0 one), is shut down and launched again from this exe, at most once in 5 min.
- **Config save.** `POST /api/config` saves, builds a new Discord notifier and new Twitch checks that keep the one 30 min restart clock, and asks the supervisor to reload. The launch guard's encoder fallback saves through the same config under the same lock, so it and a dashboard save never merge into the same old file.
- **Exit codes.** Ctrl+C, closing the console window and `POST /api/shutdown` stop the control process's own timers, close the server once the replies under way are out, and exit 0. Ctrl+C and the console closing are listened for from the start of the process until it exits, so neither reaches Windows' default handler, whose exit `START.bat` would read as a crash. The supervisor and the stream keep running: the control process never sends it `/shutdown` on its own exit. A landed update, a rollback and the test hook exit 75, once however often they are asked.
- **Updates** (`updater.rs`, `landing.rs`). The updater takes only releases with the full ZIP and `streamloop-vX.Y.Z.exe` with its checksum, and stages the exe in `_update\streamloop.exe` once its SHA-256 and its `--version` match. With `autoUpdateCheck` on, a staged update lands at 47 h 45 min of encoder uptime, after 5 min with no live encoder, or at once when the stream was stopped from the dashboard; Update Now lands it whatever the setting, and a version that rolled back once waits for Update Now. A landing stops the supervisor (20 s, then its process tree), writes `_update\landed`, renames `streamloop.exe` to `streamloop.exe.old` and the staged exe into its place, launches the supervisor from it unless the stream was held (stopped from the dashboard, waiting for Start, or a first run with no playlist saved), and exits 75. The next start confirms the update within 180 s (the new supervisor answers with the new version, with a live encoder when the stream was on air, or `streamloop.exe check` passes for a held stream) and removes `.old` and `_update\`; otherwise it puts the old exe back, keeps the record as `data\update-rolled-back` and exits 75. Nothing is checked, staged or landed while a confirmation runs, and the routes that change something, Update Now among them, answer 409. `data\update-state.json` keeps master's shape, so the dashboard's update banners work unchanged.
- **Test switches** as Node's (`STREAMLOOP_DEBUG_FAULTS`, `STREAMLOOP_TEST_HOOKS`, `STREAMLOOP_TEST_HLS_URL`, `STREAMLOOP_TEST_RELEASES`), plus `STREAMLOOP_TEST_BREAK_AT_S`, the encoder uptime at which a staged update lands.
- **API parity.** `supervisor/scripts/api-parity.mjs record --server rust` replays the dashboard's requests against `target\release\streamloop.exe`, a fake supervisor on 4417 and a temp root; `compare` checks them against Node's recording (`api-parity/node.json`), and each request records the supervisor calls it made. The fake reports the server's own version on both runs, as an R1 supervisor does. `compare` skips two differences by name: the stream key, which Node protected through a helper exe and the control process protects in-process (with the reload that follows it); and config validation errors, compared by field path rather than wording, every other key of the reply as it is.

## Native window (ui/)

- `ui/`: `streamloop-ui.exe`, a native GPUI window that does what the web dashboard does through the same REST API on 127.0.0.1:7654 (`--port N` for another port); it lives in a folder of its own beside the install, starts no process and reads nothing from the install, and is not in the release ZIPs yet.

## Invariants

- The RTMP connection survives every seam, control and feeder failure; only an encoder restart drops it. (Spike 1, spike 5)
- Nothing in `src/` imports from `spikes/`. Spike code is throwaway; what carries forward is command lines and measurements. (Notion rules; true today)
- Secrets are never committed, printed or logged. Node keeps them in gitignored `config.json` and masks them in `GET /api/config`; spike scripts read `TWITCH_STREAM_KEY` from the environment. The stream key is stored only DPAPI-protected in `config.json`, and the supervisor redacts it from every log, event and `run.json` it writes.
- The supervisor's children die with the supervisor: they live in its kill-on-close Job Object. Node spawns its own children with `cwd: SPAWN_CWD`, so none holds `app\` during an update. The supervisor itself is not Node's child; see the sibling point below.
- YouTube traffic from the supervisor goes through one gate: resolves at least 5 s apart, and a circuit breaker that stops all yt-dlp on a bot check or 3 failed resolves (backoff 1, 2, 5, 10, 30 min). A call that fails because yt-dlp cannot read the browser's cookies never counts toward the breaker: it raises `cookies-unreadable` (once per streak) and holds yt-dlp off for 60 s. A download round tries each configured player client alone, in order, and `downloads-DATE.csv` names the client of each try; a round that fails is tried again after a quarter of the time until the video airs (2 min to 1 h, logged as `retryInS`), and each video counts once toward the 3-in-a-row `downloads-failing` critical. Two downloads in a row that used a PO token and still got a 403 make the supervisor `POST /invalidate_caches` to the token server (at most every 30 min, `token-caches-cleared`), so the next token comes from a new minter.
- The exit code tells `START.bat` what to do: 0 stay down, 2 another StreamLoop is running (stay down, say so), 75 restart without a rollback check (a landed update, a rollback), anything else a crash and a restart in 10 s. `START.bat`'s parenthesised blocks use `rem`, never `::`, and the file is CRLF only (`crates/streamloop/tests/start_bat.rs`).
- New install parts are checked before they stream: `START.bat` writes `data\update-checking` before it removes `data\update-swapping`, a start that finds it holds the launch for the health check, and it goes only once the check has passed or a rollback has run. A rollback cannot put back a part that a program from outside the install holds through all its tries: that part stays new beside the old version until heal manages to put it back on a later start, and `data\update-swap.log` records it (`<folder> failed the new version stayed in use and could not be put back`).
- State is not written while a recovery or switch is in progress, so a transient position cannot overwrite the resume point.
- Media bytes never pass through a loop that also does disk writes or control work, and a critical output is never teed synchronously with a non-critical one. (Spike 1 lessons)
- The supervisor is a sibling of Node, not its child: Node restarts and app-only updates must not drop the stream; only a full update stops it, on purpose. Node starts it through `streamloop-supervisor.exe launch`, an intermediate that exits once the supervisor is up, so the supervisor's parent is dead and it has left Node's job when the job allows breakaway: no tree kill (`taskkill /T`, "End process tree") and no job of Node's reaches it.
- 2.x (from 2.3.7) will not start its OBS stream while `GET 127.0.0.1:4417/status` reports `encoder.alive: true`, so 3.0 must keep that endpoint and field. The check fails open: anything else lets 2.x stream (`src/server/stream-guard.ts` on the `2.x` branch).
- The other way round, Node does not launch the supervisor while `obs64.exe` runs, since 2.x may be streaming on the same key. Before each launch it also test-encodes with the user's `preferredEncoder` and saves a working fallback to `encoder`, or the preference again once it works (`src/server/setup-check.ts`); the supervisor reads only `encoder`.
- 2.x (from 2.3.7) only updates to releases with its own major version; 3.x releases are never marked "latest" on GitHub, because older 2.x installs still read it.
