# Architecture

How the parts fit. Direction, decisions and spike results live in the Notion pages named at the end; this file is structure only.

## What it is

Streamloop restreams a YouTube playlist to Twitch around the clock from one Windows box. This branch holds **3.1**: one Rust `streamloop.exe`, built from the Cargo workspace at the repo root, that runs as two processes. The streaming core (`streamloop.exe supervisor`, the `supervisor/` crate) plays the playlist through a headless ffmpeg pipeline and pushes RTMP itself, with no mpv, OBS or desktop session. The control process (`streamloop.exe` with no mode, `crates/control/`) serves the dashboard and its REST API, sends Discord alerts, runs the Twitch checks, launches the core and updates the exe. `START.bat` starts the control process and restarts it after a crash. Node stays in the install only to run the PO-token server. `spikes/` keeps the spikes that proved the pipeline. **3.0**, where a Node backend in `src/server/` did the control process's work, lives on the `3.0` branch; **2.x** (mpv and OBS) on the `2.x` branch.

- `src/server/index.ts`: wires every component by dependency injection, serves `/admin` and `/overlay`, opens the admin page on boot unless `autoOpenAdmin` is off, exits 75 after a staged update.
- `config.ts` / `types.ts`: Zod schema and defaults for `config.json` (gitignored), hot reload via `POST /api/config`.
- `state.ts`: playback position in `state.json`, debounced 2 s writes, suppressed during recovery.
- `mpv-client.ts` / `mpv-args.ts`: spawns mpv, talks JSON over the named pipe, polls properties, receives events.
- `recovery.ts`: 5 s heartbeat, stall / video-freeze / premature-EOF / non-playing detectors, in-place URL retry, then RetryCurrent, RestartMpv, CriticalAlert.
- `frame-monitor.ts`: hashes OBS screenshots to catch a frozen picture mpv reports as healthy.
- `obs-client.ts`: obs-websocket connection, streaming control, screenshots.
- `playlist-metadata.ts`: yt-dlp flat playlist fetch, cached for the dashboard.
- `event-store.ts`: recovery timeline as daily JSONL in `logs/`.
- `discord.ts`: webhook notifications with templates.
- `twitch.ts`: Twitch liveness check (app token + Helix streams) cross-checked with OBS's streaming state.
- `api.ts`: REST surface for the dashboard and overlay; masks secrets in `GET /api/config`.
- `updater.ts` / `ytdlp-updater.ts`: GitHub Releases updater (slim ZIP preferred, SHA-256 verified); yt-dlp self-update.
- `logger.ts` / `file-log-transport.js`: pino to console and file.
- `spawn-cwd.ts`: the temp folder every child process starts in, so nothing holds `app\` during the update swap.
- `src/admin/`: dashboard (status, timeline, transport, config, update button). `src/overlay/`: now-playing page for the OBS Browser Source.
- `scripts/START.bat`: preflight, half-swap self-heal, exit-code branching (75 update, 0 stay down, else restart in 10 s), launcher trampoline via `START.bat.new`.
- `build/prepare-release.js`: full ZIP (`node\`, `mpv\`, `yt-dlp\`, `app\`, `START.bat`) and slim update ZIP, each with `.sha256`.
- `shell/`: Tauri thin shell (stage 1 of the standalone admin UI track) that shows the local `/admin` in WebView2; not part of the release ZIP yet.

## Workspace and modes

- **Crates.** The Cargo workspace at the repo root (`workspace.package.version` is the version; `package.json` carries the same number, from which the release build names the ZIP and the exe, and a test fails when they differ): `crates/streamloop` is the exe and only dispatches on its first argument; `supervisor/` is the streaming core as a library; `crates/control` is the control process (tokio, axum, reqwest with rustls; the dashboard in `src/admin/` is built into the exe with rust-embed, and debug builds read it from disk); `crates/common` holds what both processes share (the config loader, the `/status`, `/control` and `/reload` types, the install layout, DPAPI, `procs::command`, the time helpers) and has no async runtime. Build output goes to `target\` at the root. `ui/` (R3's window), `spikes/gpui-ui`, `spikes/supervisor` and `shell/src-tauri` build on their own, outside the workspace.
- **Modes.** The first argument picks one; with none (or only `--root DIR`) the exe runs the control process, and any other argument prints the usage line and exits 64.

| Command | Runs | Started by |
|---------|------|------------|
| `streamloop.exe [--root DIR]` | the control process, in a console | `START.bat` |
| `streamloop.exe supervisor [--root DIR] [--config FILE] [--data DIR] [dev flags]` | the streaming core | the `launch` intermediate; `session.mjs` directly |
| `streamloop.exe launch --root DIR [--debug-faults]` | the intermediate that starts the core detached and exits | the control process's launcher |
| `streamloop.exe check [--root DIR]` | proves the core runs, without streaming | the control process, to confirm an update while the stream is held |
| `streamloop.exe protect` | DPAPI helper on stdin | the harness only; the control process protects in-process |
| `streamloop.exe --version` | prints the version and exits 0 | the updater's check of a staged exe, `verify-release.mjs`, the harness |

- **Process tree.** `START.bat`, then the control process, which runs `launch`, which exits and leaves the supervisor with a dead parent in its own kill-on-close job. The control process never enters that job.

## Supervisor interface

- **Install layout** under the root (`crates/common/src/paths.rs`): `streamloop.exe`, `ffmpeg\ffmpeg.exe`, `yt-dlp\yt-dlp.exe`, `yt-dlp\deno.exe`, `yt-dlp\plugins\`, `pot\build\main.js` (token server), `node\node.exe` (runs only the token server), `supervisor\slate.mp4`, `app\config.json`, `app\config.example.json`, `app\logs\` (the control process's log and timeline), `data\`. While an update is on its way: `_update\streamloop.exe` (staged), `_update\landed` (written by a landing), `streamloop.exe.old` (the previous exe until the update is confirmed) and, after a rollback, `streamloop.exe.bad`. Every tool is called by full path, never through PATH; yt-dlp gets `--ffmpeg-location` for its merge.
- **Packaging** (`build/prepare-release.js`): `cargo build --release -p streamloop` at the repo root, then the install layout in `build/release-layout.js`: `streamloop.exe`, `START.bat`, `app\config.example.json`, `supervisor\slate.mp4`, `ffmpeg\`, `yt-dlp\` (with deno and the plugin zip), `pot\`, `node\` and `data\`, plus `README.txt` (`scripts/README.txt`). `pot\` is the bgutil token server (2.0.0) built under the bundled Node. The build writes `dist/streamloop-vX.Y.Z.zip`, `dist/streamloop-vX.Y.Z.exe` (the updater's download), a `.sha256` for each and `dist/node-version.txt`; there is no update ZIP and no `components.json`. No ZIP ships `app\config.json`; the control process creates it from `config.example.json` on first start, so a reinstall keeps the user's. `crates/streamloop/tests/release_layout.rs` checks the layout against `Layout` in `crates/common/src/paths.rs`, and `build/verify-release.mjs` checks the ZIP and that its exe prints the ZIP's version.
- **CLI.** `streamloop.exe supervisor [--root DIR] [--config FILE] [--data DIR]`; the default root is the exe's own folder. Dev only: `--target URL` (replaces ingest and key, for local MediaMTX) and `--debug-faults`, which also unlocks the test knobs (`--url-ttl-s`, `--url-refresh-margin-s`, `--limit-rate`, `--start`, `--max-videos`, `--hours`). `streamloop.exe launch ARGS` starts `streamloop.exe supervisor ARGS` through a short-lived intermediate: it re-execs the same exe detached, in a new process group and outside the caller's job (`CREATE_BREAKAWAY_FROM_JOB`; when the job refuses breakaway it starts inside the job instead), logs a `launched` event with `breakaway: true|false`, waits up to 3 s for the port to answer or the child to exit, and exits 2 when the child found the port taken, 3 when it refused `config.json`, else 0. The supervisor binds its port before it reads `config.json`, so 2 only ever means the port is taken; a refused config logs a critical `config-refused` event with the reason and exits 3. Any other exit during the wait is 1. `streamloop.exe check` (the same flags as `supervisor`) proves the binary runs without streaming: it reads `config.json` as startup does, requires every install-layout file, runs `ffmpeg -version` and starts the token server on port 4418, pinging `/ping` once a second until it answers, for up to 15 s from its start (the grace the supervisor's own token watchdog gives a new server), then stops it; it binds neither 4417 nor 4416, enters no job and touches neither cache nor state. It prints `ok` and exits 0, else prints `streamloop-supervisor check: <reason>` on stderr and exits 1; the control process strips that prefix when it confirms an update. `streamloop.exe protect` reads a stream key on stdin and prints a DPAPI blob (current user) for `supervisor.streamKeyProtected`.
- **Config** (`app\config.json`, owned by the control process): `playlists` (each `id`, in play order) plus a `supervisor` object: `ingestUrl`, `streamKeyProtected`, `encoder`, `cacheBudgetMb`, `readAheadSeconds`, `playerClient`, `overlay`, `freezeSeconds`, `silenceSeconds` (minimums: read-ahead 2 s, freeze and silence 5 s, cache 50 MB), and the top-level `ytdlCookiesFromBrowser` it shares with the control process (empty for none; passed to every yt-dlp call as `--cookies-from-browser`, applied live). The supervisor reads it read-only through `streamloop_common::config`, the loader the control process uses: a blank `ingestUrl` or `playerClient` and a missing `supervisor` object mean the defaults, and an empty `streamKeyProtected` means no key. Read at start and on `POST /reload`, which applies what it can live, reports `restartRequired` for ingest, key, encoder and the freeze and silence durations, and brings the ring in line with `playlists` (see Playlists under Main flows). Nothing writes the order back: it stays as the user set it.
- **HTTP** on 127.0.0.1:4417 (the request and reply shapes live in `streamloop_common::api`): `GET /status` (`state`: `starting`, `playing`, `recovering`, `needs-stream-key`, `waiting-for-playlist`, `stopping`; `reason`; `streamKeyProblem`; now playing, with `playing.playlistId` naming the list on air, and `playing.index` and `playlistCount` counting within it; `version` (the exe's build version); encoder alive, speed, CPU and `uptimeS` (whole seconds since the encoder started, `null` with none); watchdog; YouTube breaker; token server), `POST /control` (`{"cmd"}`: `next` and `prev`, which cross into the neighbouring list at a list's end, `restart`, `jump` with an `index` in the list on air and an optional video `id` that wins when the ring has it, or `restart-encoder` with an optional `reason` of up to 200 characters), `POST /reload` (optional `{"playlist", "index", "id"}`: `playlist` goes to that configured list and refuses any other, `index` and `id` say where in it to start, by id when the list has it, else the index clamped to the list; a supervisor before `playlist` existed plays only `playlists[0]` and names no list in `/status`, and the control process then answers that the full ZIP is needed), `POST /shutdown`, and `POST /debug/fault` only with `--debug-faults`. With no usable key it stays up in `needs-stream-key` and a reload with a working key starts the encoder.
- **Data** (`data\`): `state.json` (resume point: the list on air, the video's id and number in that list, its position), `cache\` (finished `<id>.mp4` downloads survive a restart and count toward the budget once a list names them; partial files are removed at start, and files no video claims once every configured list has answered), `logs\` with daily files (`supervisor-events-DATE.jsonl`; up to 3.0.4 it was `events-DATE.jsonl`, which the control process still reads; `seams-`/`controls-`/`encoder-`/`downloads-`/`deletes-`/`buffer-DATE.csv`, `ytdlp-`/`tokenserver-DATE.log`), one log per ffmpeg process, `run.json` and `playlist.json` (the list on air with its playlist id, played when the fetch at start fails); a week is kept and the key is redacted from all of it. Video numbers in events and CSVs count within their list, so `id` is what tells two lists' videos apart. The control process keeps its own files here too: `stopped-by-user` (written on the dashboard's Stop, removed on Start and read at every start, so a stopped stream stays stopped across restarts), `waiting-for-start` (a start held until Start, so a crash restart keeps holding), `setup-check.json` (the last setup check), `update-state.json` (a landing and its confirmation: from and to version, step, result, reason, in the shape the dashboard's update banner reads) and `update-rolled-back` (the record of an update that was rolled back; that version then waits for Update Now).
- **Twitch read-back** (the control process, `readback.rs`): every 5 min while live, two frames of the channel's own HLS 5 s apart through `ffmpeg\ffmpeg.exe`; if the overlay clock stands still twice in a row while Helix says live, the control process asks for `restart-encoder`, at most once per 30 min (a clock it shares with the Helix check), then only alerts.
- **Launch** (the control process, `launcher.rs`): it polls `GET /status` every 2 s and, after 3 misses, runs `ROOT\streamloop.exe launch --root ROOT` hidden and with no stdio (backoff 10 s, 30 s, 60 s, 5 min, reset after 60 s running). An exit code 2 from the intermediate within 5 s of the spawn means another supervisor holds the port, and the control process attaches to it. Exit 3 counts as down, and `/api/status` shows "The supervisor refused config.json: <reason>" (from the last `config-refused` event) until a supervisor answers. `POST /api/config` refuses a `ytdlCookiesFromBrowser` over 200 characters or with a control character, so a save cannot write a config the supervisor refuses. `START.bat` sets `STREAMLOOP_START` (`first` after the window opens, `restart` after any other exit, `rollback` for the first start after its rollback); with `autoStartStream` off, a `first` start holds the launch (`data\waiting-for-start`, launcher state `ready`) until Start, and a `restart` keeps holding only while that marker exists. Recovery ignores that hold: a supervisor that answers is attached and ends it, and one that dies is relaunched. An update never changes whether the stream is held: a start that finds `_update\landed`, and a `rollback` start, hold only when the record (`_update\landed`, or `data\update-rolled-back` for a rollback) says the stream was held before the landing; any other launches as usual, so a launch the guard held during the landing is tried again within the confirmation. A `rollback` start whose record cannot be read follows `autoStartStream`. A supervisor that reports another version than the control process, or none (a 3.0 one), is shut down (its `version` and `encoder.alive` are read even when the rest of its status does not parse) and launched again from this exe, at most once in 5 min, unless the stream was stopped from the dashboard. It never stops the supervisor otherwise, except for the dashboard's Stop stream, after which it relaunches nothing until Start. `STREAMLOOP_DEBUG_FAULTS=1` adds `--debug-faults`, for test runs only.
- **Measuring harness:** `supervisor/scripts/` (`dev-root.mjs` builds a dev root in this layout, with the built exe linked as `ROOT\streamloop.exe`; `session.mjs` runs one supervisor session, `streamloop.exe supervisor`, against local MediaMTX, `drive.mjs` drives it over HTTP only, `analyze.mjs` computes the verdict; `node-session.mjs` starts `ROOT\streamloop.exe` from a launcher console as `START.bat` does and drives the control process's API through runs A, B, C and treekill, telling the control process and the supervisor apart by command line, and prints each run's verdict; `install-session.mjs` installs `dist/`'s full ZIP in a temp folder and takes it through exe updates (planned break, Update Now, a landing while stopped), both rollbacks, the move from v3.0.5 and the gate's faults, against a local release list given by `STREAMLOOP_TEST_RELEASES` and test builds of `streamloop.exe` it makes with cargo; `install-kit.mjs` holds the helpers, the test builds and the release list it shares with R3's `ui-session.mjs`; `api-parity.mjs` records the dashboard API's answers and compares them with Node's recording).

## Main flows

- **Seam.** A new feeder starts when the timeline is less than 20 s ahead of the encoder. It begins at timeline offset = last video PTS written + one frame, so timestamps stay continuous. The encoder never sees a seam as anything but more MPEG-TS.
- **Playlists.** Every configured list's videos sit in one ring, in the configured order rotated to start at the list loaded first, so each list keeps the one that follows it. Seams, look-ahead downloads, retries and skips work on ring positions and never see a list boundary: the last video of a list is followed by the next list's first video like any other seam, and the last list by the first. A single list wraps to its own first video. The list a start or reload asks for loads first; the others join behind it one at a time once a video is on air and none waits for YouTube. A list that will not load is reported once (`playlist-failed`), tried again every 10 min, and counts toward the breaker only for a bot check. When a list ends while another is still missing, `playlist-advance` or `playlist-restart` goes critical, since that is when it costs viewers something. A list joining at the end moves no video; a reorder or a dropped list lays the ring out again and jumps to the video on air at its position. A reload naming a list in the ring jumps there without a fetch, and a reload naming none stays on the list on air while the config has it.
- **Control (next, prev, restart, jump).** All four are `switch(index, 0)` computed from `P_view` (what the viewer sees, not what the feeder has reached): kill the feeder, flush the queue from the first video PES at least 1 s past the writer, start the target feeder on the continuing offset from the cached file or, if not on disk, its URL (slate covers the resolve). Last command wins. `restart-encoder` (for the control process's Twitch checks) takes the encoder-down path of recovery step (3) and logs `encoder-restart-requested` with the caller's reason; while a restart is already pending it answers `alreadyRestarting: true`, and in `needs-stream-key` it answers 400.
- **Cold start.** The list `state.json` names is fetched first, or the first configured one if the config no longer has it or `state.json` names none (a position saved for a list that is no longer configured is not used); if that fails and `playlist.json` holds the same playlist id, that list plays (`playlist-from-saved`) while the fetch is retried through the gate. A resume whose video is in the cache plays from the file at once, with no slate wait and no resolve. Otherwise: slate on air at once; the first video's URL is resolved (`yt-dlp -j`, waits for `available_at`) and switched in; the downloader fetches that video first; when the file is complete the URL feeder is killed and a file feeder continues at `P_fed` with no flush.
- **Recovery.** (1) Feeder fails, stalls (no video PES for 10 s) or ends early: restart in place at `P_fed`, 2 tries per video. A file feeder that fails before its first frame drops its cached file, so the retry plays the URL; a later failure keeps the file and retries from it. A picture the encoder's `freezedetect` finds frozen for `freezeSeconds` (counted from 5 s into a seam, never on the slate) takes the same ladder: retry, retry, skip. Audio silent for `silenceSeconds` is reported only (outcome `content`): the feeder carries audio and video as one stream, so a broken audio stream stalls the feeder or ends it early, which step (1) catches, while silence under a moving picture is the video's own ("brb" stretches). Silence never restarts or skips anything. (2) Then skip; 3 skips in a row is critical. A video YouTube will not serve (removed, private, blocked, age-gated) is skipped at once; from the third such video in a row (no successful resolve between them) each one counts toward the breaker. When every video has been skipped, the slate airs for 60 s, doubling to 30 min, before the list is tried again. (3) Encoder exits or its progress stops for 10 s: restart with backoff (2, 5, 10, 30, 60 s); current video resumes at `P_view`. While it waits, a thread off the control loop tries a TCP connection to the ingest every 2 s (port 1935 for `rtmp://` and 443 for `rtmps://` when the URL names none, as Twitch's does), and an ingest seen down that answers again restarts the encoder at once (`encoder-start` carries `ingestBack: true`). The `encoder-exit` event carries `uptimeS`; the control process reads a first exit after 47.5 h as Twitch's 48 h broadcast limit and sends no Discord alert for it or its restart. (4) Supervisor crash: Job Object kills every child, the control process relaunches it, it resumes from `state.json`.
- **Exe update.** See Updates under Control process. The stream is off air from the supervisor's stop to the new supervisor's start, about 9 s on the dev machine; the control process restarts after it, and the stream does not wait for that.

## Control process

`streamloop.exe [--root DIR]` runs the control process (`crates/control`), the port of 3.0's Node backend (`src/server/` on the `3.0` branch): the dashboard and its REST API on 127.0.0.1:7654, Discord, the Twitch checks, the launcher and the updater. Each Node module has a Rust module with the same behaviour, timings and texts; `app.rs` is `index.ts`.

- **Root and files.** `--root`, else the exe's folder when it holds `app\`, else `STREAMLOOP_ROOT`; with none it prints "No install root: run streamloop.exe from the install folder, or pass --root." and exits 1. A root that did not come from the exe's folder is dev mode, where the updater only checks. It reads `ROOT\app\config.json` (created from `app\config.example.json` when missing) and writes its log (`streamloop-DATE.log`) and timeline (`events-DATE.jsonl`) to `ROOT\app\logs\`, in release and dev alike, 7 days kept. The dashboard's files are built into the exe.
- **Start order**, as `index.ts`: load the config; bind the port (taken: "Port 7654 is in use. Is another StreamLoop running? Close it and start this one again." and exit 2, so `START.bat` can tell another StreamLoop from a crash); remove the 3.0 leftovers; settle an update that was cut off (a failed or rolled-back result, such as a rollback by `START.bat`, goes to the timeline and out once as a critical), or start confirming one that landed; the launcher, the events tail and the Twitch checks unless it is a first run (the wizard's first save starts them); the update checks (30 s after start, then every `updateCheckIntervalMs` while `autoUpdateCheck` is on) once no confirmation runs; the yt-dlp self-update; `autoOpenAdmin`.
- **3.0 leftovers**, removed by name at every start: `app\src`, `app\node_modules`, `app\package.json`, `app\package-lock.json`, `app\tsconfig.json`, `app\node-version.txt`, `supervisor\streamloop-supervisor.exe`, `_update_tmp\`, `_update_old\`, `START.bat.new`, `_apply_launcher.bat`, and what an unreleased build of 3.0's full update could leave: `_update_old_<part>\`, `_update_bad_<part>\`, `_update_bad_app\`, `data\update-swapping`, `data\update-checking` and `data\update-swap.log`. `app\config.json`, `app\logs\`, `data\` and `_update\` stay.
- **Launcher.** See Launch under Supervisor interface. The control process keeps its stdin, stdout and stderr out of its children, so the supervisor holds neither its console nor a file its output was redirected to, and a launcher that redirects to that file can start it again. Before each launch it refuses while `obs64.exe` runs and test-encodes with `preferredEncoder` (see Invariants).
- **Config save.** `POST /api/config` saves, builds a new Discord notifier and new Twitch checks that keep the one 30 min restart clock, and asks the supervisor to reload. The launch guard's encoder fallback saves through the same config under the same lock, so it and a dashboard save never merge into the same old file.
- **Exit codes.** Ctrl+C, closing the console window and `POST /api/shutdown` stop the control process's own timers, close the server once the replies under way are out, and exit 0. A landing that has begun to stop the supervisor finishes first (up to 90 s), so the exit does not leave the stream stopped; one that has not gives up. Ctrl+C and the console closing are listened for from the start of the process until it exits, so neither reaches Windows' default handler, whose exit `START.bat` would read as a crash. The supervisor and the stream keep running: the control process never sends it `/shutdown` on its own exit. A config that does not load exits 1, a taken port 2, an unknown argument 64, and a landed update, a rollback and the test hook 75, once however often they are asked.
- **Updates** (`updater.rs`, `landing.rs`). The updater takes only releases with the running major version (prereleases count from 3 up; drafts and tags that are not `vX.Y.Z` do not) that carry the full ZIP and `streamloop-vX.Y.Z.exe` with its checksum (`streamloop-vX.Y.Z.exe.sha256` only; `streamloop-vX.Y.Z.sha256` is the ZIP's), so a release still uploading and every 3.0.x release are skipped. It downloads only from `github.com` and `objects.githubusercontent.com`, and stages the exe in `_update\streamloop.exe` once its streamed SHA-256 matches and it prints `X.Y.Z` to `--version` within 10 s; a stage that fails says why in the notice line and is tried again at the next check. With `autoUpdateCheck` on, a staged update lands at 47 h 45 min of encoder uptime (just before Twitch's 48 h cut, which it replaces), after 5 min with no live encoder, or when the stream was stopped from the dashboard (seen on two polls in a row, or with the supervisor gone, so the Stop and Start of Restart stream land nothing); Update Now lands it whatever the setting, staging first if needed, and a version that rolled back once waits for Update Now. A landing posts "Installing StreamLoop X.Y.Z. The stream restarts." (or "The stream stays stopped." when it was held) to the timeline and to Discord, stops the supervisor (20 s, then its process tree), writes `_update\landed`, renames `streamloop.exe` to `streamloop.exe.old` and the staged exe into its place (Windows lets a running exe be renamed, not overwritten; a failed second rename puts `.old` back and relaunches the old supervisor), launches the supervisor from it unless the stream was held (stopped from the dashboard, waiting for Start, or a first run with no playlist saved), and exits 75. The next start confirms the update within 180 s (the new supervisor answers with the new version, with a live encoder when the stream was on air, or `streamloop.exe check` passes for a held stream), removes `.old` and `_update\`, and adds "Updated to StreamLoop X.Y.Z." to the timeline; otherwise it puts the old exe back (`streamloop.exe.bad`), keeps the record as `data\update-rolled-back`, relaunches the supervisor from the old exe, sends a critical and exits 75. Nothing is checked, staged or landed while a confirmation runs, and the routes that change something, Update Now among them, answer 409; Stop is let through during the confirmation (not during the landing), as the way out of a new version that airs badly, and the check then confirms the update. The banner's notice line (`nodeNotice`) says when a staged update installs, and adds the Node notice when the release's `node-version.txt` names another Node than `node\node.exe`.
- **`START.bat`** (`scripts/START.bat`) is a short launcher around `streamloop.exe`; it swaps nothing and replaces nothing, itself included. Preflight: an exe left as `streamloop.exe.old` by an update cut off between its two renames is renamed back (again before every run), then `streamloop.exe`, `ffmpeg\ffmpeg.exe`, `node\node.exe` and `pot\build\main.js` must exist. It runs `streamloop.exe` in a loop: 0 stays down, 2 (another StreamLoop holds the port) stays down with a message, 75 restarts after 10 s, anything else is a crash and restarts after 10 s. After a crash with `_update\landed` and `streamloop.exe.old` present, the new exe stopped before it confirmed itself, so `:rollback` puts the previous exe back (`streamloop.exe` becomes `streamloop.exe.bad`, `.old` becomes `streamloop.exe`, `_update\landed` moves to `data\update-rolled-back`) and prints a `[RECOVER]` line; the old control process then finds the new supervisor and replaces it by the version rule. Each rename is checked: when one fails (antivirus or an indexer holding the file), the first is undone if it worked, a `[WARN]` line is printed and `_update\landed` stays, so the next crash tries again.
- **Test switches**, never set by `config.json` or a release: `STREAMLOOP_DEBUG_FAULTS`, `STREAMLOOP_TEST_HOOKS` (`POST /api/test/exit-75`), `STREAMLOOP_TEST_HLS_URL` (the read-back reads this HLS and the channel counts as live), `STREAMLOOP_TEST_RELEASES` (a local release list, assets only from 127.0.0.1) and `STREAMLOOP_TEST_BREAK_AT_S` (the encoder uptime at which a staged update lands). The `streamloop` crate's features `test-supervisor-fails` and `test-control-fails` make a test build whose supervisor or control mode exits at start; the release build turns neither on.
- **API parity.** `supervisor/scripts/api-parity.mjs record --server rust` replays the dashboard's requests against `target\release\streamloop.exe`, a fake supervisor on 4417 and a temp root; `compare` checks them against Node's recording (`api-parity/node.json`), and each request records the supervisor calls it made. The recording was made before 3.1 removed the Node backend and stays as it is; `--server node` no longer runs. The fake reports the server's own version, as a 3.1 supervisor does. `compare` skips two differences by name: the stream key, which Node protected through a helper exe and the control process protects in-process (with the reload that follows it); and config validation errors, compared by field path rather than wording, every other key of the reply as it is.

## Native window (ui/)

- `ui/`: `streamloop-ui.exe`, a native GPUI window that does what the web dashboard does through the same REST API on 127.0.0.1:7654 (`--port N` for another port); it lives in a folder of its own beside the install, starts no process and reads nothing from the install, and is not in the release ZIPs yet.

## Invariants

- The RTMP connection survives every seam, control and feeder failure; only an encoder restart drops it. (Spike 1, spike 5)
- Nothing in `crates/`, `supervisor/` or `src/admin/` imports from `spikes/`. Spike code is throwaway; what carries forward is command lines and measurements. (Notion rules; true today)
- Secrets are never committed, printed or logged. The control process keeps them in gitignored `config.json` and masks them in `GET /api/config`; spike scripts read `TWITCH_STREAM_KEY` from the environment. The stream key is stored only DPAPI-protected in `config.json`, and the supervisor redacts it from every log, event and `run.json` it writes.
- Every child process starts through `streamloop_common::procs::command`: the temp folder as its working folder and no window (`crates/streamloop/tests/repo_guards.rs` fails on any other `Command::new`). The supervisor's children die with the supervisor: they live in its kill-on-close Job Object. The supervisor itself is not the control process's child; see the sibling point below.
- YouTube traffic from the supervisor goes through one gate: resolves at least 5 s apart, and a circuit breaker that stops all yt-dlp on a bot check or 3 failed resolves (backoff 1, 2, 5, 10, 30 min). A call that fails because yt-dlp cannot read the browser's cookies never counts toward the breaker: it raises `cookies-unreadable` (once per streak) and holds yt-dlp off for 60 s. A download round tries each configured player client alone, in order, and `downloads-DATE.csv` names the client of each try; a round that fails is tried again after a quarter of the time until the video airs (2 min to 1 h, logged as `retryInS`), and each video counts once toward the 3-in-a-row `downloads-failing` critical. Two downloads in a row that used a PO token and still got a 403 make the supervisor `POST /invalidate_caches` to the token server (at most every 30 min, `token-caches-cleared`), so the next token comes from a new minter.
- The exit code tells `START.bat` what to do: 0 stay down, 2 another StreamLoop is running (stay down, say so), 75 restart without a rollback check (a landed update, a rollback), anything else a crash and a restart in 10 s. `START.bat`'s parenthesised blocks use `rem`, never `::`, and the file is CRLF only (`crates/streamloop/tests/start_bat.rs`).
- An update replaces only `streamloop.exe`, by two renames, and the previous exe stays as `streamloop.exe.old` until the new version is confirmed; until then a failed confirmation (the control process) or a crash of the new control process (`START.bat`) puts it back. The two processes always run the same version: a supervisor of another version is replaced.
- State is not written while a recovery or switch is in progress, so a transient position cannot overwrite the resume point.
- Media bytes never pass through a loop that also does disk writes or control work, and a critical output is never teed synchronously with a non-critical one. (Spike 1 lessons)
- The supervisor is a sibling of the control process, not its child: a control process crash, restart or tree kill must not drop the stream; only an update stops it, on purpose. The control process starts it through `streamloop.exe launch`, an intermediate that exits once the supervisor is up, so the supervisor's parent is dead and it has left the control process's job when the job allows breakaway: no tree kill (`taskkill /T`, "End process tree") and no job of the control process's reaches it.
- 2.x (from 2.3.7) will not start its OBS stream while `GET 127.0.0.1:4417/status` reports `encoder.alive: true`, so 3.x must keep that endpoint and field. The check fails open: anything else lets 2.x stream (`src/server/stream-guard.ts` on the `2.x` branch).
- The other way round, the control process does not launch the supervisor while `obs64.exe` runs, since 2.x may be streaming on the same key. Before each launch it also test-encodes with the user's `preferredEncoder` and saves a working fallback to `encoder`, or the preference again once it works (`crates/control/src/setup_check.rs`); the supervisor reads only `encoder`.
- 2.x (from 2.3.7) only updates to releases with its own major version; 3.x releases are never marked "latest" on GitHub, because older 2.x installs still read it.
